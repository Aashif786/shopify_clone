# ADR-006: Idempotency Strategy

## Status

**Accepted**

## Date

2026-10-07

## Decision

The platform will use **application-level idempotency backed by PostgreSQL** for business operations where retries could otherwise create duplicate side effects.

Idempotency will be implemented deliberately per operation rather than by applying a generic middleware layer to every endpoint.

Critical operations such as payments, checkout completion, order creation, webhook processing, and selected background jobs must define explicit idempotency behavior.

---

## 1. Context

Distributed systems retry.

Requests may be repeated because of:

- Network timeouts.
- Browser retries.
- Client retries.
- Load balancer retries.
- Worker retries.
- Process crashes.
- Webhook redelivery.
- External provider retries.
- Users submitting the same action multiple times.

For a commerce platform, duplicate execution can cause serious consequences:

```text id="c6y4m8"
Duplicate payment
Duplicate order
Duplicate inventory reservation
Duplicate discount usage
Duplicate webhook effect
```

The platform therefore requires explicit idempotency guarantees for critical operations.

---

## 2. Decision Drivers

The strategy is based on:

- Payment safety.
- Checkout correctness.
- Order correctness.
- Inventory correctness.
- Webhook reliability.
- Worker retry safety.
- PostgreSQL as source of truth.
- Multi-tenant isolation.
- Simple Demo infrastructure.
- Future scalability.
- Clear operational behavior.

---

## 3. Definition

An operation is idempotent when repeating the same logical request does not produce additional unintended business effects.

Conceptually:

```text id="m8f3s1"
Request A
   ↓
Business effect
   ↓
Retry Request A
   ↓
Same result / no duplicate effect
```

Idempotency does not necessarily mean that every repeated HTTP request returns byte-for-byte identical output.

It means the business operation is safely repeatable according to its contract.

---

## 4. Scope

Idempotency is required where duplicate execution could cause material harm.

Primary candidates include:

- Checkout completion.
- Payment creation.
- Order creation.
- Refund operations.
- Webhook processing.
- Inventory reservation where retries can duplicate effects.
- External side-effecting integrations.
- Background jobs with non-idempotent effects.

Read-only operations normally do not require idempotency keys.

---

## 5. PostgreSQL as Idempotency Store

PostgreSQL will be the authoritative store for Demo idempotency records.

This avoids introducing Redis or another dedicated state store solely for idempotency.

Conceptually:

```text id="z6n2p5"
Request
   ↓
Idempotency record
   ↓
Business operation
   ↓
Persist result
```

---

## 6. Idempotency Key

Clients performing supported operations provide a unique idempotency key.

The key should be:

- Opaque.
- Unique within its intended scope.
- Stable across retries.
- Generated by the caller.
- Validated for reasonable length and format.

The API contract must document where the key is supplied.

---

## 7. Idempotency Scope

An idempotency key must be scoped correctly.

A key should not accidentally collide across unrelated tenants or operations.

Conceptually:

```text id="p7x3m4"
Store
+
Operation
+
Idempotency Key
```

may form the uniqueness boundary.

The exact database constraint depends on the operation.

---

## 8. Request Fingerprint

The system should associate an idempotency key with the relevant request identity.

This prevents:

```text id="h3k8s5"
Key = ABC
Request = Payment $100
```

from later being reused as:

```text id="d9w2q6"
Key = ABC
Request = Payment $500
```

The second request must not silently reuse the first request's result.

---

## 9. Idempotency Conflict

If an existing idempotency key is reused with a materially different request, the API should return a clear conflict.

Example:

```text id="x1m7q4"
IDEMPOTENCY_CONFLICT
```

The operation must not execute the second request.

---

## 10. Idempotency Record

A conceptual record may contain:

```text id="b8c4r1"
id
store_id
operation
idempotency_key
request_fingerprint
status
response_status
response_body
resource_type
resource_id
created_at
completed_at
expires_at
```

The exact schema may differ by implementation.

Sensitive request or response data should not be stored unnecessarily.

---

## 11. Idempotency States

A typical state model is:

```text id="f5q9s2"
new
 ↓
processing
 ↓
completed
```

Failure behavior may allow:

```text id="u4j7p8"
processing
   ↓
failed/retryable
   ↓
retry
```

The exact state machine depends on the operation.

---

## 12. Atomic Claiming

Two concurrent requests using the same idempotency key must not both execute the business operation.

The database must provide an atomic mechanism such as:

- Unique constraint.
- Transaction.
- Row locking.
- Atomic insert.

Conceptually:

```text id="k2r6v9"
Request A ─┐
           ├── same key
Request B ─┘
              ↓
         One logical operation
```

---

## 13. Concurrent Requests

For concurrent requests using the same key:

### Request A

Claims the key and begins processing.

### Request B

Must not independently execute the same business operation.

It should:

- Wait where appropriate.
- Return the completed result if available.
- Return an appropriate in-progress response.
- Retry according to the API contract.

The exact behavior must be defined by the endpoint.

---

## 14. Transaction Boundary

Where possible, idempotency state and the corresponding business mutation should participate in the same transaction.

Example:

```text id="q7n3c6"
BEGIN
   ↓
Claim idempotency key
   ↓
Perform business mutation
   ↓
Persist result
   ↓
COMMIT
```

This prevents a successful business operation from being forgotten by the idempotency layer.

---

## 15. External API Calls

External API calls create an additional consistency boundary.

Avoid:

```text id="s9d4x1"
BEGIN
  ↓
External Payment API
  ↓
Database mutation
  ↓
COMMIT
```

because external calls should not be held inside long database transactions.

Instead, the integration must use a provider-specific idempotency or reconciliation strategy.

---

## 16. Payment Idempotency

Payment creation is a critical idempotency case.

The platform must prevent:

```text id="m1c8v5"
User clicks Pay
       ↓
Payment succeeds
       ↓
Network timeout
       ↓
User retries
       ↓
Second charge
```

The implementation should combine:

- Internal idempotency.
- Provider idempotency where supported.
- Payment attempt records.
- Webhook reconciliation.

---

## 17. Provider Idempotency

If the payment provider supports its own idempotency key, the platform should use a stable provider-facing key derived from the internal operation.

The internal and provider idempotency records must remain correlated.

---

## 18. Payment Webhooks

Payment webhooks must be idempotent independently of payment creation requests.

The system should persist the provider event identifier.

Conceptually:

```text id="n4x7q2"
Provider Event ID
       ↓
Unique constraint
       ↓
Process once
```

Duplicate delivery must not create duplicate business effects.

---

## 19. Webhook Ordering

Webhooks may arrive:

- More than once.
- Out of order.
- After a delayed network connection.
- After an application deployment.

The processing logic must not assume perfect delivery ordering unless the provider guarantees it.

Where necessary, the application should reconcile the authoritative provider state.

---

## 20. Checkout Idempotency

Checkout completion is a critical operation.

Repeated completion requests must not create:

- Multiple orders.
- Multiple payments.
- Multiple inventory deductions.
- Multiple discount usages.

The checkout workflow should have an explicit idempotency boundary.

---

## 21. Order Creation Idempotency

If order creation is independently exposed as a mutation, it must define its idempotency semantics.

The platform should associate repeated requests with the same logical operation.

An existing successful order should be returned or referenced rather than creating another order.

---

## 22. Inventory Idempotency

Inventory operations require special consideration.

A simple "set quantity" operation may naturally be idempotent:

```text id="c9r2x6"
Set available = 10
Set available = 10
```

An adjustment operation is not naturally idempotent:

```text id="f8m4q1"
Increase quantity by 5
Increase quantity by 5
```

If retried, it could incorrectly increase inventory twice.

Therefore, inventory adjustments that can be retried must have an explicit idempotency mechanism.

---

## 23. Discount Usage

Discount usage updates may require idempotency when the same checkout operation can be retried.

The system must not count the same logical redemption multiple times.

The exact constraint and usage model must follow the discount specification.

---

## 24. Refund Idempotency

Refund operations must be safe against repeated requests.

A retry must not accidentally create multiple refunds against the same payment/order amount.

Refund identity should be associated with:

- Internal refund operation.
- Provider refund identifier where available.
- Idempotency key.

---

## 25. Background Jobs

Jobs must be idempotent where execution can repeat.

A worker may execute a job twice because:

```text id="v3y6q8"
Worker crashes
       ↓
Job becomes retryable
       ↓
Another worker executes
```

The second execution must not create unintended duplicate effects.

---

## 26. Job-Level Idempotency

A job may use:

- Job ID.
- Business resource ID.
- Provider operation ID.
- Explicit deduplication key.

The correct identity depends on the job.

The system must not assume that the job ID alone prevents duplicate external effects.

---

## 27. Notifications

Notifications may be duplicated during retries.

Where duplicate delivery is harmful, use a durable notification/delivery identity.

For example:

```text id="j4q7n1"
Order ID
+
Notification Type
+
Recipient
```

may define a logical notification identity.

The exact uniqueness boundary depends on the notification model.

---

## 28. Idempotency and Events

Events represent facts.

An event handler should therefore tolerate duplicate event delivery.

For example:

```text id="z2m8c4"
OrderCreated
   ↓
Notification Handler
   ↓
Already processed?
   ↓
Yes → No duplicate effect
```

Event consumers must not assume exactly-once delivery.

---

## 29. Exactly-Once Semantics

The system should not rely on true distributed exactly-once execution.

Instead, it should implement:

```text id="q8v5k2"
At-least-once delivery
+
Idempotent processing
+
Durable state
```

This provides practical business-level correctness.

---

## 30. Idempotency Expiration

Idempotency records may require retention/expiration.

The retention period should reflect the operation.

Short-lived UI mutations may require shorter retention.

Financial operations may require longer retention or permanent business records.

Expiration must never remove information required to preserve financial or audit correctness.

---

## 31. Stored Responses

For selected APIs, the completed idempotency record may store enough information to reproduce the previous response.

Where response storage is unnecessary, the record may instead reference the resulting resource.

Example:

```text id="w6r2p9"
Idempotency record
      ↓
Order ID
      ↓
Reconstruct current response
```

The chosen strategy must be documented per operation.

---

## 32. Sensitive Data

Idempotency records must not unnecessarily store:

- Passwords.
- Authentication tokens.
- Payment credentials.
- Full card information.
- Secrets.
- Large customer payloads.

Request fingerprints should preferably use a safe representation rather than storing the complete request.

---

## 33. Request Fingerprinting

A request fingerprint may be generated from a canonical representation of relevant request data.

The system should ensure that equivalent requests produce consistent fingerprints.

Changes to meaningful request fields must produce different fingerprints.

---

## 34. Error Handling

Idempotency-aware operations must distinguish:

```text id="r5k1m8"
First request failed before effect
        ↓
Safe retry

First request succeeded
        ↓
Return/reconstruct existing result

Same key + different request
        ↓
Conflict

Operation still processing
        ↓
Defined in-progress behavior
```

---

## 35. API Contract

The API documentation must explicitly identify which mutations support idempotency.

For supported endpoints, document:

- Header or request mechanism.
- Required format.
- Scope.
- Retry behavior.
- Conflict behavior.
- Retention.
- In-progress behavior.

---

## 36. Testing

Idempotency must be tested at multiple levels.

### Unit tests

- Fingerprint calculation.
- Conflict detection.
- State transitions.

### Integration tests

- Database uniqueness.
- Concurrent requests.
- Transaction behavior.
- Retry behavior.

### E2E tests

- User retry after timeout.
- Duplicate checkout submission.
- Duplicate payment attempt.
- Webhook redelivery.

---

## 37. Required Concurrent Test

At least one integration test must execute concurrent requests with the same idempotency key.

Expected result:

```text id="h2p7n5"
Request A ───────→ Business effect
Request B ───────→ Same logical result
```

The test must prove that the business effect occurs only once.

---

## 38. Failure Scenario Testing

Tests should include:

- Crash before idempotency record creation.
- Crash after claiming key.
- Crash after business mutation.
- External timeout after provider success.
- Duplicate webhook.
- Same key with different request.
- Retry after temporary failure.

The expected recovery behavior must be explicit.

---

## 39. Observability

Idempotency-related logs should include safe operational identifiers such as:

- Operation type.
- Idempotency key hash/reference where appropriate.
- Request ID.
- Resource ID.
- Outcome.

Do not log sensitive request bodies.

Useful metrics include:

- Idempotent requests.
- Duplicate requests.
- Idempotency conflicts.
- In-progress collisions.
- Provider duplicate events.

---

## 40. Tenant Isolation

Idempotency keys must be tenant-scoped appropriately.

A key generated by Store A must not interfere with an unrelated operation in Store B.

Database uniqueness constraints and application authorization must both enforce the intended boundary.

---

## 41. Security

The idempotency system must not become an authorization bypass.

A repeated request must still belong to an authorized caller and tenant.

For example:

```text id="y4n8s6"
Valid key
+
Unauthorized caller
=
Denied
```

An idempotency key is not a credential.

---

## 42. Performance

Idempotency checks should be indexed appropriately.

Expected lookup dimensions should have supporting indexes or unique constraints.

The idempotency layer must not become a database bottleneck for ordinary read-only operations.

---

## 43. Rejected Alternatives

### No Idempotency

Rejected because duplicate payments, orders, inventory effects, and webhook processing would create unacceptable correctness risks.

### In-Memory Idempotency

Rejected because process restarts would lose state.

### Redis-Only Idempotency

Rejected for the Demo because it introduces an additional infrastructure dependency when PostgreSQL already provides durable transactional state.

### Global Middleware for Every Endpoint

Rejected because not every operation requires idempotency and different business operations have different semantics.

---

## 44. Migration Path to V1

The Demo should isolate idempotency persistence behind an application/persistence interface.

Conceptually:

```text id="n3x6q1"
Application Operation
       ↓
Idempotency Interface
       ↓
PostgreSQL Implementation
```

Future infrastructure may use:

```text id="b7k4m9"
Application Operation
       ↓
Idempotency Interface
       ↓
Redis / Distributed Store
```

only if scale or operational requirements justify it.

Business semantics must remain stable even if storage changes.

---

## 45. Consequences

### Positive

- Prevents duplicate critical business effects.
- Protects payment correctness.
- Protects checkout/order correctness.
- Handles webhook redelivery.
- Supports safe worker retries.
- Uses existing PostgreSQL infrastructure.
- Keeps Demo operationally simple.

### Negative

- Additional database state.
- Additional transaction complexity.
- Each operation requires explicit semantics.
- Retention and cleanup require consideration.
- External integrations still require provider-specific reconciliation.

These costs are accepted because commerce correctness is more important than eliminating a few database rows.

---

## 46. Definition of Done

The idempotency strategy is implemented when:

```text id="c5m9r3"
[ ] Idempotency persistence exists
[ ] Scope is explicitly defined
[ ] Request fingerprinting exists where required
[ ] Duplicate keys cannot execute the operation twice
[ ] Same-key/different-request conflicts are handled
[ ] Concurrent duplicate requests are tested
[ ] Checkout completion is protected
[ ] Payment operations are protected
[ ] Order creation is protected where applicable
[ ] Refund operations are protected
[ ] Inventory adjustments are protected where required
[ ] Webhooks are duplicate-safe
[ ] Background jobs are retry-safe
[ ] External provider idempotency is used where available
[ ] Sensitive data is excluded from idempotency records
[ ] Tenant isolation is enforced
[ ] API behavior is documented
[ ] Failure scenarios are tested
[ ] Observability exists
[ ] No unnecessary dedicated infrastructure is required for Demo
```
