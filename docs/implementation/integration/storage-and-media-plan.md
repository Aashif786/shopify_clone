# Storage and Media Plan

## 1. Purpose

This document defines how binary media and persistent application data are stored in the Demo.

The primary goal is to keep PostgreSQL authoritative for transactional metadata while using object storage for binary content.

The design must support reliable uploads, tenant isolation, controlled access, cleanup, and future CDN integration without requiring a fundamental redesign.

---

# 2. Storage Responsibilities

The Demo uses different storage systems for different types of data.

```text
PostgreSQL
    ↓
Transactional application data

Object Storage
    ↓
Binary media

Application Logs / Monitoring
    ↓
Operational telemetry
```

PostgreSQL remains the authoritative source of business state.

---

# 3. PostgreSQL Storage

PostgreSQL stores structured application data such as:

- Stores.
- Products.
- Variants.
- Inventory.
- Customers.
- Carts.
- Discounts.
- Checkout records.
- Payments.
- Orders.
- Media metadata.
- Notifications.
- Jobs.
- Webhook records.

Business-critical relationships and constraints belong in PostgreSQL.

---

# 4. Object Storage

Object storage is used for binary files such as:

- Product images.
- Store images.
- Logos.
- Other supported media assets.

Large binary files should not be stored directly in PostgreSQL.

---

# 5. Media Architecture

The basic architecture is:

```text
Browser
   ↓
Web Application
   ↓
Media Application Service
   ↓
Object Storage
   +
PostgreSQL Metadata
```

The application controls authorization and metadata ownership.

---

# 6. Media Ownership

The Media module owns:

- Media records.
- Upload lifecycle.
- Storage object references.
- File metadata.
- Access behavior.
- Cleanup state.

Business modules own their relationship to media.

For example:

```text
Products
    ↓
Product Media Association

Media
    ↓
Object Storage Metadata
```

The Product module does not own the storage implementation.

---

# 7. Media Record

A media record should contain sufficient information to manage the object without storing the binary content itself.

Conceptually:

```text
Media
├── id
├── storeId
├── objectKey
├── filename
├── contentType
├── size
├── status
├── visibility
├── metadata
├── createdAt
├── updatedAt
└── deletedAt
```

The exact schema belongs to the database implementation.

---

# 8. Store Ownership

Every media record must have explicit Store ownership where applicable.

Conceptually:

```text
Store
   ↓
Media
   ↓
Object Storage Object
```

A media object must never be accessible merely because a user knows its object key.

---

# 9. Object Key Design

Object keys should be generated by the application.

A conceptual structure is:

```text
stores/{storeId}/media/{mediaId}/{generated-name}
```

The exact structure may evolve.

Object keys must not be directly constructed from raw user-provided filenames.

---

# 10. Object Key Requirements

Object keys should:

- Be deterministic where useful.
- Avoid unsafe characters.
- Avoid path traversal.
- Avoid exposing sensitive information.
- Include tenant/store ownership where appropriate.
- Be unique enough to prevent collisions.

User filenames may be retained as metadata but should not be trusted as storage paths.

---

# 11. Upload Lifecycle

Media should use an explicit lifecycle.

Example:

```text
PENDING
   ↓
UPLOADING
   ↓
READY
```

Failure may result in:

```text
UPLOADING
   ↓
FAILED
```

Deletion may result in:

```text
READY
   ↓
DELETING
   ↓
DELETED
```

The exact state machine must remain consistent with the media specification.

---

# 12. Upload Flow

A normal upload should follow:

```text
1. Authenticate user
2. Resolve Store
3. Authorize media operation
4. Validate upload metadata
5. Create media record
6. Upload object
7. Verify upload result
8. Mark media READY
9. Associate media with domain resource
```

The exact ordering may differ when direct-to-storage uploads are introduced.

---

# 13. Upload Failure

If the object upload fails:

```text
Media
    ↓
FAILED
```

The system must not expose the media as successfully available.

Failed metadata records may be retained temporarily for diagnosis and cleanup.

---

# 14. Direct-to-Object-Storage Uploads

The Demo may initially route uploads through the application if traffic is small.

If direct uploads are needed:

```text
Browser
   ↓
Request upload authorization
   ↓
Application
   ↓
Signed upload
   ↓
Object Storage
```

The application must still create and own the Media record.

---

# 15. Direct Upload Verification

When using direct uploads, the application must verify that:

- The upload belongs to the expected media record.
- The object exists.
- The object belongs to the correct Store.
- The expected size/type constraints are satisfied.
- The upload has not expired.

The client must not be trusted to declare an upload complete.

---

# 16. Content-Type Validation

Client-provided MIME types should not be treated as authoritative.

Validation may consider:

- Declared content type.
- File extension.
- Actual content where practical.
- Maximum size.
- Supported media types.

Unsupported or suspicious files must be rejected.

---

# 17. File Size Limits

Upload limits should be configured centrally.

Limits should exist at multiple layers where appropriate:

```text
Client
   ↓
Application
   ↓
Object Storage
```

The application must enforce the authoritative business limit.

---

# 18. Image Processing

The Demo should avoid building a complex image-processing pipeline unless required.

Basic capabilities may include:

- Validation.
- Metadata extraction.
- Optional resizing.
- Optional thumbnail generation.

Advanced transformations can be introduced later.

---

# 19. Media Access

Media should support controlled visibility.

Typical categories:

```text
Public
Private
```

Public media may be referenced by storefront pages.

Private media requires authorization before access is granted.

---

# 20. Signed Access

Private objects should use short-lived signed URLs or an equivalent controlled-access mechanism.

Conceptually:

```text
Authorized Request
      ↓
Media Authorization
      ↓
Signed URL
      ↓
Object Storage
```

The application should not expose permanent private storage credentials.

---

# 21. Public Storefront Media

Published product media may be publicly accessible when the product and Store permit it.

Publication state must still be respected.

For example:

```text
Unpublished Product
    ↓
Media should not automatically become public storefront content
```

---

# 22. Media and Products

Products reference media through explicit associations.

The Product module controls:

- Which media belongs to a product.
- Display ordering.
- Primary media selection.
- Product-level publication relationship.

The Media module controls storage lifecycle.

---

# 23. Media and Store Configuration

Store configuration may reference media such as:

- Store logo.
- Store branding image.

Store configuration owns the business relationship.

Media owns the underlying file.

---

# 24. Deletion Strategy

Deleting a domain resource should not necessarily immediately delete its media object.

A safer lifecycle may be:

```text
Domain Association Removed
        ↓
Media Becomes Unreferenced
        ↓
Cleanup Process
        ↓
Object Deleted
```

This reduces accidental data loss.

---

# 25. Orphan Detection

The system should be able to identify:

- Media records without associations.
- Objects without valid metadata.
- Failed uploads.
- Deleted records whose objects remain.
- Metadata pointing to missing objects.

Cleanup should be recoverable and observable.

---

# 26. Cleanup Jobs

Media cleanup should be performed asynchronously.

Example:

```text
Media marked for deletion
        ↓
Cleanup Job
        ↓
Object Storage
        ↓
Delete / Verify
        ↓
Update Media State
```

The cleanup operation must be idempotent.

---

# 27. Storage Failure Handling

Object storage failures must not corrupt application state.

Examples:

### Upload failure

```text
Media remains FAILED or recoverable
```

### Delete failure

```text
Media remains DELETING
```

and can be retried.

### Temporary provider outage

```text
Retryable operation
```

---

# 28. Database and Object Storage Consistency

PostgreSQL and object storage do not share the same transaction.

Therefore, operations involving both must use explicit intermediate states.

Do not assume:

```text
DB COMMIT = Object Storage COMMIT
```

They are separate systems.

---

# 29. Example Upload Consistency

```text
Create Media(PENDING)
        ↓
Commit
        ↓
Upload Object
        ↓
Verify Object
        ↓
Mark Media READY
```

If the upload fails, the Media record remains recoverable rather than falsely reporting success.

---

# 30. Example Deletion Consistency

```text
Mark Media DELETING
        ↓
Commit
        ↓
Delete Object
        ↓
Mark Media DELETED
```

If deletion fails, the operation can be retried safely.

---

# 31. Transaction Boundaries

Do not hold a database transaction open while waiting for object storage.

Avoid:

```text
BEGIN
 ↓
Upload large file
 ↓
Wait
 ↓
COMMIT
```

Use short transactions around metadata state changes.

---

# 32. Tenant Isolation

Every media operation must verify Store ownership.

Required checks include:

- Upload.
- Read metadata.
- Generate access URL.
- Associate media.
- Remove association.
- Delete media.
- Cleanup.

A user from Store A must not access Store B's media even if the media identifier is known.

---

# 33. Authorization

Media authorization should distinguish:

```text
Merchant
Customer
Public Storefront
Internal Worker
```

Permissions depend on the operation.

For example:

- Merchant may upload product media.
- Customer may view public product media.
- Worker may perform cleanup.
- Public users cannot access private merchant media.

---

# 34. Media and Background Jobs

Background jobs may perform:

- Cleanup.
- Verification.
- Thumbnail generation.
- Metadata processing.
- Retry of failed operations.

Job handlers must be idempotent.

---

# 35. Media and Notifications

Media should not be directly responsible for sending notifications.

If an upload event needs to trigger another action:

```text
Media Event
    ↓
Event Consumer
    ↓
Relevant Application Operation
```

---

# 36. Storage Credentials

Object-storage credentials must:

- Remain server-side.
- Never enter browser bundles.
- Never be committed.
- Never be logged.
- Use least privilege.
- Be rotatable.

Where possible, separate credentials should be used for different environments.

---

# 37. Local Development

Local development should provide a predictable storage mechanism.

Options include:

```text
Local filesystem
or
S3-compatible local object storage
```

The chosen implementation should preserve the same application-level storage interface used in production.

---

# 38. Storage Abstraction

The application should define an internal storage interface such as:

```text
ObjectStorage
├── put()
├── get()
├── delete()
├── exists()
└── createSignedUrl()
```

The exact interface should contain only operations actually required by the application.

---

# 39. Storage Adapter

The provider implementation belongs behind the interface:

```text
Media Application Service
        ↓
ObjectStorage
        ↓
ObjectStorageAdapter
        ↓
Provider
```

This prevents provider-specific APIs from spreading through the codebase.

---

# 40. Local and Production Adapters

A practical Demo setup may use:

```text
Development
    ↓
Local / S3-compatible storage

Production
    ↓
Managed Object Storage
```

Both must satisfy the same internal contract.

---

### Integration

# 43. Storage Monitoring

Monitor:

- Upload failures.
- Download failures where observable.
- Object-storage latency.
- Storage provider errors.
- Failed cleanup jobs.
- Orphaned media.
- Storage usage.
- Large upload failures.

---

# 44. Storage Cost Control

The Demo should avoid unnecessary storage costs.

Controls include:

- File-size limits.
- Supported-format restrictions.
- Cleanup of orphaned objects.
- Cleanup of failed uploads.
- Avoiding duplicate objects where appropriate.
- Retention policies where appropriate.

---

# 45. Future CDN Integration

The architecture should allow:

```text
Storefront
    ↓
CDN
    ↓
Object Storage
```

without changing Media ownership.

The CDN remains a delivery optimization layer rather than the source of truth.

---

# 46. Future Media Processing

Future V1 capabilities may include:

- Image transformation.
- Responsive image generation.
- Thumbnail pipelines.
- Video processing.
- Virus/malware scanning.
- Content moderation.
- CDN optimization.

These should be added only when product requirements justify them.

The Demo requires only:

```text

[ ] Upload
```

---

# 49. Final Principle

PostgreSQL owns **what the application knows about a media object**.

Object storage owns **the binary object itself**.

The application owns the relationship between them.

```text
PostgreSQL
    │
    │ metadata / ownership / lifecycle
    ↓
Media Module
    │
    │ storage abstraction
    ↓
Object Storage
    │
    ↓
Binary Data
```

This separation keeps transactional business data reliable while allowing media storage to scale independently as the platform grows.
