    # Media Integration Build Implementation

## 1. Purpose

This document defines the concrete implementation approach for media handling in the Demo.

The Media integration provides a controlled abstraction for uploading, storing, associating, serving, and deleting binary assets such as product images.

The implementation must keep binary storage outside PostgreSQL while keeping authoritative media metadata and relationships inside PostgreSQL.

---

# 2. Ownership

The Media integration owns:

- Media metadata.
- Object-storage abstraction.
- Upload lifecycle.
- Object keys.
- File validation.
- Media associations.
- Public/private access decisions.
- Signed URL generation where required.
- Cleanup of abandoned objects.
- Media deletion.
- Storage-provider isolation.

It does not own:

- Product business rules.
- Store lifecycle.
- Product publication.
- Catalog behavior.
- Customer profiles.
- Order history.

---

# 3. Storage Architecture

The Demo should use:

```text
Application
    ↓
Media service/interface
    ↓
Object Storage Adapter
    ↓
Object Storage
```

PostgreSQL stores metadata:

```text
Media
Media relationships
Store ownership
Object key
Content metadata
Lifecycle state
```

The binary object itself remains in object storage.

---

# 4. Module Location

Implementation belongs under the approved integration location:

```text
modules/media/
```

or the repository location established by the existing media implementation specification.

Recommended structure:

```text
modules/media/
├── domain/
├── application/
├── infrastructure/
└── index.ts
```

Provider-specific implementation must remain behind the public Media interface.

---

# 5. Object Storage Adapter

Application code must not depend directly on a provider SDK.

Use an abstraction such as:

```text
MediaStorage
├── upload
├── delete
├── exists
└── createAccessUrl
```

The concrete provider adapter implements this interface.

This keeps migration between object-storage providers possible without changing domain logic.

---

# 6. Demo Storage Provider

The Demo may use an S3-compatible object-storage provider.

The provider is an infrastructure decision, not a domain dependency.

The implementation should avoid provider-specific types leaking into:

```text
Products
Stores
API DTOs
UI
Domain entities
```

---

# 7. Media Metadata

A Media record should contain the information required to manage the object safely.

Typical fields include:

```text
id
storeId
objectKey
originalFilename
contentType
size
visibility
status
createdAt
updatedAt
```

Additional metadata should be added only when required.

---

# 8. Store Ownership

Every Media record must belong to a Store.

This provides the tenant boundary:

```text
Store
  ↓
Media
  ↓
Object
```

A Store must never be able to retrieve or mutate another Store's Media.

---

# 9. Object Key Design

Object keys must be generated by the server.

Do not use raw user-provided filenames as object keys.

A key may conceptually follow:

```text
stores/{storeId}/media/{mediaId}/{generated-name}
```

The exact naming convention should be centralized.

---

# 10. Object Key Security

Object keys must not allow:

```text
../
absolute filesystem paths
provider bucket traversal
unexpected path injection
```

Keys should be generated from trusted identifiers and controlled values.

---

# 11. Original Filename

The original filename may be retained for user display.

It must not be treated as a trusted storage path.

Filename values should be normalized and safely encoded when displayed.

---

# 12. File Validation

Uploads must be validated server-side.

Validation should include:

```text
Content type
File size
Allowed extension where appropriate
Actual file characteristics where practical
```

Do not trust only the browser-provided MIME type.

---

# 13. Allowed Media Types

Demo requirements should initially remain narrow.

For product media, typical supported types may include:

```text
image/jpeg
image/png
image/webp
```

Additional formats should be introduced only when required.

---

# 14. File Size Limits

Maximum upload size must be explicitly configured.

The limit should be enforced:

```text
At API boundary
Before storage
```

where the architecture allows.

Do not allow unlimited request bodies.

---

# 15. Upload Flow

A controlled upload should follow:

```text
Client
  ↓
Authenticated request
  ↓
Store authorization
  ↓
Upload validation
  ↓
Media metadata creation
  ↓
Object upload
  ↓
Media becomes usable
```

The exact sequence must account for failure recovery.

---

# 16. Upload Consistency

PostgreSQL and object storage are separate systems.

There is no distributed transaction between them.

Therefore the implementation must explicitly handle:

```text
Database succeeds, object upload fails
Object upload succeeds, database operation fails
Network timeout during upload
Client retries upload
```

---

# 17. Pending Media State

A Media lifecycle may include a temporary state such as:

```text
PENDING
READY
FAILED
DELETED
```

This prevents incomplete uploads from appearing as usable media.

The exact state model follows the Media specification.

---

# 18. Database-First vs Object-First

The implementation must choose one controlled upload strategy and define its recovery behavior.

A practical approach is:

```text
Create pending Media record
        ↓
Upload object
        ↓
Mark Media READY
```

If upload fails:

```text
Media → FAILED
```

and cleanup can be performed asynchronously.

---

# 19. Direct-to-Object Uploads

If direct browser-to-object-storage uploads are used, the server must first authorize the upload and generate a controlled upload target.

The client must not receive unrestricted bucket credentials.

Conceptually:

```text
Client
  ↓
Request upload authorization
  ↓
Server validates Store + file constraints
  ↓
Server creates controlled upload target
  ↓
Client uploads object
  ↓
Server verifies/finalizes Media
```

---

# 20. Media Finalization

When direct upload is used, finalization must verify enough metadata to prevent a client from claiming an arbitrary object is valid.

Verification should include appropriate:

```text
Store ownership
Object key
Expected content type
Expected size
Media identity
```

---

# 21. Public vs Private Media

Media must explicitly define visibility.

Possible states:

```text
PUBLIC
PRIVATE
```

Product images intended for the public Storefront may be public.

Merchant/private assets should remain private.

---

# 22. Public Access

Public media may use a stable public URL or controlled CDN/object-storage URL.

The URL must not expose:

```text
private bucket credentials
storage secrets
internal filesystem paths
```

---

# 23. Private Access

Private media should be accessed through authorized application flows or short-lived signed URLs.

Authorization must happen before generating access.

---

# 24. Signed URLs

Signed URLs should:

- Have limited lifetime.
- Be generated server-side.
- Be scoped to the intended object.
- Never contain long-lived credentials.

The application should not expose storage credentials to browsers.

---

# 25. Media Associations

Media can be associated with domain resources through explicit relationships.

For Demo, Product media is the primary use case.

Conceptually:

```text
Product
  ↓
ProductMedia
  ↓
Media
```

The Products domain controls whether a media asset is valid for a Product.

---

# 26. Product Ownership Boundary

Media owns the file.

Products owns the meaning of the file within the catalog.

For example:

```text
Media:
"What binary object exists?"

Products:
"Is this the primary image for Product X?"
```

This prevents Media from becoming a generic business-logic dumping ground.

---

# 27. Store Deletion

If a Store is deleted or deactivated according to the approved lifecycle, associated media must follow the defined retention/cleanup policy.

Do not immediately delete objects unless the business lifecycle explicitly permits it.

---

# 28. Product Deletion

Deleting a Product association does not necessarily mean deleting the Media object.

The system must distinguish:

```text
Association removed
```

from:

```text
Media permanently deleted
```

This avoids accidentally deleting an asset still referenced elsewhere.

---

# 29. Orphaned Objects

Object storage may contain objects that no longer have valid database metadata because of partial failures.

A background cleanup process should identify and remove safe orphaned objects according to the approved retention period.

Do not perform aggressive immediate deletion based solely on a transient database error.

---

# 30. Database Constraints

The database should enforce:

```text
Media → Store foreign key
Media identity uniqueness
Object key uniqueness where required
Association foreign keys
Appropriate uniqueness for Product/Media relationships
```

The exact constraints follow the database specification.

---

# 31. Transactions

Database transactions should cover related metadata changes.

They must not hold a database transaction open while waiting for slow external object-storage operations unless the operation absolutely requires it.

Prefer:

```text
Short DB transaction
        ↓
External storage operation
        ↓
Short DB finalization transaction
```

where appropriate.

---

# 32. External Failure Handling

Storage-provider failures should be translated into controlled application errors.

The application must distinguish:

```text
Validation failure
Authorization failure
Provider unavailable
Timeout
Object not found
Permanent provider error
```

---

# 33. Retry Behavior

Retryable object-storage failures may be retried.

Retries must use bounded attempts and backoff.

The system must not retry indefinitely.

---

# 34. Idempotent Upload Handling

Upload retries must not unintentionally create uncontrolled duplicate Media records.

Where the workflow requires it, use an idempotency key or upload identity.

The exact semantics must match the API idempotency architecture.

---

# 35. Delete Behavior

Media deletion should be treated as a coordinated operation:

```text
Validate authorization
        ↓
Validate Media state
        ↓
Remove association where required
        ↓
Delete object
        ↓
Update Media lifecycle
```

The implementation must account for provider failures.

---

# 36. Deletion Recovery

If database state and object storage disagree after deletion, the system should preserve enough state for cleanup/reconciliation.

Do not silently assume an external deletion succeeded merely because the request was sent.

---

# 37. API Boundary

Media APIs should expose explicit DTOs.

For example:

```text
MediaDTO
MediaUploadRequestDTO
MediaUploadResponseDTO
MediaAccessDTO
```

Do not serialize storage-provider responses directly.

---

# 38. Merchant Authorization

Media management requires authenticated Store membership and the appropriate permission.

At minimum:

```text
Create Media
View permitted Media
Associate Media
Delete Media
```

must be separately considered.

---

# 39. Storefront Authorization

Public Storefront access must only expose media marked for public use and belonging to the requested Store.

A public media URL must never become a mechanism for discovering private objects.

---

# 40. API Input Validation

Validate:

```text

Product ID
Store context
Content type
File size
Filename

```

Client-provided object keys must never become authoritative storage locations.


# 50. Final Principle

Media storage should be treated as an infrastructure capability with a strict application boundary:

```text
Business Domain
      ↓
Media Application Interface
      ↓
Storage Adapter
      ↓
Object Storage
```

PostgreSQL remains authoritative for **what media exists, who owns it, and how it is associated**.

Object storage remains authoritative for **the binary content itself**.

Keeping those responsibilities separate prevents the media system from contaminating the commerce domains with provider-specific storage logic while leaving a clean path toward CDN-backed and larger-scale media infrastructure later.
