# Media Implementation Specification

## 1. Purpose

This document defines the implementation requirements for the **Media** capability of the Cal Cart commerce platform.

The Media capability provides controlled storage and retrieval of files used by Stores and their products while keeping binary storage separate from PostgreSQL transactional data.

---

## 2. Scope

The Media capability owns:

- Media metadata.
- File upload coordination.
- Object-storage integration.
- Media ownership.
- Media type validation.
- File size validation.
- Upload lifecycle.
- Media association with supported domain entities.
- Public/private access policy.
- Media deletion.
- Upload failure cleanup.

It does not own:

- Product business logic.
- Product publication.
- Store configuration.
- Inventory.
- Orders.
- Customer profiles.
- Image editing.
- CDN infrastructure.

---

## 3. Module Location

Implementation belongs under:

```text
modules/media/
```

Recommended structure:

```text
modules/media/
├── application/
├── domain/
├── infrastructure/
├── presentation/
└── index.ts
```

The module should expose public interfaces for other modules rather than allowing direct access to its internal storage implementation.

---

## 4. Storage Architecture

Binary files should not be stored directly in PostgreSQL.

The Demo architecture should use:

```text
Application
    ↓
Media Service
    ↓
Object Storage
    ↓
Stored File
```

PostgreSQL stores metadata:

```text
Media Record
    ↓
Object Storage Key
```

This keeps transactional database growth under control and allows object storage/CDN infrastructure to evolve independently.

---

## 5. Media Entity

Conceptually:

```text
Media
├── id
├── storeId
├── objectKey
├── originalFileName
├── contentType
├── sizeBytes
├── status
├── visibility
├── checksum?
├── metadata?
├── createdAt
└── updatedAt
```

The exact schema may evolve based on the selected object-storage provider.

---

## 6. Store Ownership

Every Media record must belong to a Store where the media is Store-scoped.

Conceptually:

```text
Organization
    ↓
Store
    ↓
Media
```

The Store ID must be persisted as authoritative ownership information.

---

## 7. Tenant Isolation

Media access must always be tenant-aware.

A request for:

```text
Store A → Media X
```

must never accidentally retrieve:

```text
Store B → Media X
```

Media IDs alone must not be treated as sufficient authorization context.

---

## 8. Media Status

A practical lifecycle is:

```text
PENDING
READY
FAILED
DELETED
```

### PENDING

Metadata exists and upload is expected or in progress.

### READY

Object exists and passed validation.

### FAILED

Upload or processing failed.

### DELETED

Media is no longer available for normal use.

---

## 9. Upload Lifecycle

A typical upload flow:

```text
Client
  ↓
Request Upload
  ↓
Validate Store Authorization
  ↓
Validate File Metadata
  ↓
Create PENDING Media
  ↓
Generate Object Key
  ↓
Upload Object
  ↓
Verify Upload
  ↓
Mark Media READY
```

The database must not mark media `READY` before the corresponding object is safely available.

---

## 10. Upload Strategy

For the Demo, the application may coordinate uploads directly or issue short-lived signed upload URLs.

A preferred scalable model is:

```text
Client
   ↓
Request Upload
   ↓
Server validates request
   ↓
Server creates PENDING Media
   ↓
Signed Upload URL
   ↓
Client uploads directly to Object Storage
   ↓
Server confirms upload
   ↓
Media becomes READY
```

The implementation must ensure that clients cannot use arbitrary object-storage paths.

---

## 11. Object Keys

Object keys should be generated by the server.

Example conceptual structure:

```text
stores/{storeId}/media/{mediaId}/{generated-name}
```

Object keys should not depend directly on user-provided filenames.

User-provided filenames may be retained separately as display metadata.

---

## 12. Filename Handling

Original filenames must be treated as untrusted input.

The system should:

- Validate length.
- Normalize where appropriate.
- Prevent path traversal.
- Never use the filename directly as an object-storage path.
- Preserve it only as metadata when useful.

Examples of unsafe values must not influence storage paths:

```text
../../file
..\..\file
/etc/passwd
```

---

## 13. Allowed Media Types

The Demo should explicitly define supported media types.

Typical initial support:

```text
image/jpeg
image/png
image/webp
```

Additional types such as:

```text
image/gif
video/mp4
application/pdf
```

should only be enabled where an actual product requirement exists.

---

## 14. MIME-Type Validation

The client-provided MIME type must not be trusted blindly.

Where practical, the server or upload-processing layer should verify the actual file signature/content type.

The declared content type and detected type should be checked for consistency.

---

## 15. File Size Limits

Each media category must have explicit size limits.

For example:

```text
Images → configured maximum
Videos → configured maximum
Documents → configured maximum
```

Limits must be enforced before accepting unnecessarily large uploads.

The exact limits belong in configuration rather than scattered throughout application code.

---

## 16. Media Metadata

Metadata may include:

- Original filename.
- Content type.
- File size.
- Checksum.
- Width.
- Height.
- Duration where applicable.

Metadata must not be trusted merely because the client supplied it.

---

## 17. Image Dimensions

For supported images, the system may extract:

```text
width
height
```

from the actual file.

This allows the application to validate excessively large or malformed images.

---

## 18. Checksums

A checksum may be stored for:

- Upload verification.
- Duplicate detection.
- Integrity verification.
- Operational diagnostics.

Checksums must not replace authorization or ownership checks.

---

## 19. Media Associations

Media should be associated with domain entities through explicit relationships.

For example:

```text
Store
  └── Media

Product
  └── ProductMedia
        └── Media
```

The Products module owns product-specific ordering and meaning.

The Media module owns the underlying media record and storage lifecycle.

---

## 20. Product Media

A product may contain multiple media objects.

The product-media relationship should support:

- Ordering.
- Primary/featured media.
- Association removal.
- Media replacement.

Example:

```text
Product
├── Media A → position 0 → primary
├── Media B → position 1
└── Media C → position 2
```

The Products module should control product presentation semantics.

---

## 21. Media Ownership vs Association

The system must distinguish:

```text
Media ownership
```

from:

```text
Domain association
```

A Media object belongs to a Store.

A Product may reference that Media object.

Deleting a Product must not automatically delete shared media unless the ownership policy explicitly requires it.

---

## 22. Public vs Private Media

Media must have an explicit visibility policy.

For example:

```text
PUBLIC
PRIVATE
```

Public product media may be exposed through storefront delivery.

Private media must require authorization before access.

---

## 23. Signed URLs

Private or controlled media may use short-lived signed URLs.

Signed URLs should:

- Expire.
- Be scoped to the intended object.
- Not expose storage credentials.
- Be generated server-side.

---

## 24. Public Media URLs

Public media URLs should not expose sensitive storage credentials or internal configuration.

The application may expose:

```text
https://cdn.example.com/...
```

or an equivalent public media URL.

The exact CDN strategy is infrastructure-specific.

---

## 25. Object Storage Abstraction

Object storage must be accessed through an abstraction.

Conceptually:

```text
Media Application Service
        ↓
ObjectStorage interface
        ↓
ObjectStorageAdapter
        ↓
Provider
```

The Media module must not spread provider-specific SDK calls throughout domain logic.

---

## 26. Object Storage Interface

A conceptual interface may support:

```text
createUploadTarget()
put()
get()
head()
delete()
exists()
createSignedUrl()
```

Only the operations actually required by the Demo should be implemented.

---

## 27. Transaction Boundaries

Database transactions must remain short.

Do not keep a PostgreSQL transaction open while waiting for a potentially slow object-storage upload.

Prefer:

```text
Create metadata
    ↓
Commit
    ↓
Upload object
    ↓
Verify
    ↓
Update metadata
```

Recovery must handle failures between these stages.

---

## 28. Upload Failure

If object upload fails:

```text
PENDING
   ↓
FAILED
```

or the pending record may be cleaned up according to the implementation policy.

Failed objects and metadata must not remain indefinitely without lifecycle handling.

---

## 29. Orphaned Objects

The system must account for cases such as:

```text
Object uploaded
   ↓
Database update fails
```

This can create an orphaned object.

A background cleanup job may identify and remove abandoned objects where safe.

---

## 30. Missing Objects

The reverse case must also be handled:

```text
Database says READY
   ↓
Object no longer exists
```

The application must fail safely rather than returning misleading media data.

Operational monitoring should identify unexpected missing objects.

---

## 31. Media Deletion

Deletion should be coordinated between:

```text
Database metadata
Object Storage
```

A safe approach should prevent references to media that the system considers permanently deleted.

The exact ordering must account for failure recovery.

---

## 32. Association Deletion

Removing a Product → Media association should not necessarily delete the Media object.

Example:

```text
Remove ProductMedia
       ↓
Media remains available
```

Actual media deletion should follow the ownership/lifecycle policy.

---

## 33. Media Replacement

When replacing a Product's primary image:

```text
Upload new Media
      ↓
Verify READY
      ↓
Update ProductMedia association
      ↓
Optionally clean up old Media
```

The new media must be valid before the product loses its previous valid media.

---

## 34. Authorization

Media operations must enforce authorization appropriate to the action.

Examples:

- Store Staff may upload if permitted.
- Store Staff may manage Product media if permitted.
- Customers may only access media intended for them/public storefront use.
- Public storefront users must never access private Store media.

Authorization must be evaluated server-side.

---

## 35. Input Validation

Validate:

- Store ID/context.
- Media ID.
- Filename.
- Content type.
- File size.
- Association target.
- Visibility.
- Ordering values.

Never trust client-provided object keys.

---

## 36. API Endpoints

Potential merchant APIs:

```text
POST   /api/v1/media/uploads
GET    /api/v1/media/{mediaId}
DELETE /api/v1/media/{mediaId}
POST   /api/v1/media/{mediaId}/complete
```

Product association APIs may belong to the Products capability:

```text
POST   /api/v1/products/{productId}/media
DELETE /api/v1/products/{productId}/media/{mediaId}
PATCH  /api/v1/products/{productId}/media/order
```

The exact API surface should follow the API architecture and module ownership rules.

---

## 37. Storefront Media Access

Storefront APIs should expose only media that is valid for public presentation.

The storefront should not expose:

- Private media.
- Failed media.
- Deleted media.
- Media belonging to another Store.

---

## 38. Database Constraints

The database should enforce appropriate relationships and constraints.

Examples:

```text
media.store_id → stores.id
product_media.media_id → media.id
product_media.product_id → products.id
```

Foreign keys must prevent invalid references.

---

## 39. Indexing

Useful indexes include:

```text
media(store_id)
media(store_id, status)
media(store_id, created_at)
product_media(product_id, position)
product_media(media_id)
```

Indexes should reflect actual access patterns rather than being added indiscriminately.

---

## 40. Idempotency

Upload initiation and media association operations should have clearly defined retry semantics.

For example, retrying an association request should not create duplicate ProductMedia records.

Where appropriate, use:

```text
unique(product_id, media_id)
```

or an equivalent domain constraint.

---

## 41. Events

Useful domain events may include:

```text
MediaCreated
MediaReady
MediaUploadFailed
MediaDeleted
MediaAssociated
MediaDisassociated
```

Events represent facts that have already occurred.

They must not be used as an excuse to bypass transactional correctness.

---

## 42. Background Jobs

Potential background jobs include:

- Expire abandoned uploads.
- Clean orphaned objects.
- Verify missing objects.
- Delete deferred media.
- Generate future media derivatives.

The Demo should implement only jobs that are actually required.

---

## 43. Image Processing

The Demo should avoid building a complete image-processing pipeline unless required.

Basic processing may include:

- Metadata extraction.
- Validation.
- Optional thumbnail generation.

Advanced transformations can be added later.

---

## 44. Security Requirements

The Media implementation must protect against:

- Path traversal.
- Malicious file types.
- Oversized uploads.
- Unauthorized Store access.
- Cross-tenant media access.
- Object-key manipulation.
- Credential exposure.
- Malicious filenames.
- Untrusted metadata.
- Public exposure of private files.

---

## 45. Malware Scanning

Malware scanning is not required for every Demo upload by default.

If business requirements introduce untrusted document uploads, scanning should be added before the file becomes usable by sensitive workflows.

---

## 46. Logging

Safe operational logs may include:

```text
mediaId
storeId
operation
status
sizeBytes
contentType
requestId
```

Do not log:

- Signed URLs containing sensitive tokens.
- Storage credentials.
- Private object contents.
- Authentication cookies.

---

Test:

- Filename validation.
- MIME validation.
- File-size validation.
- Media state transitions.
- Object-key generation.
- Visibility rules.

### Integration Tests

Test:

- Media metadata persistence.
- Object-storage adapter.
- Upload lifecycle.
- Failed uploads.
- Deletion.
- Product associations.

### Security Tests

Test:

- Cross-tenant access.
- Unauthorized deletion.
- Private media access.
- Object-key manipulation.
- Oversized uploads.
- Invalid file types.

### E2E Tests

Test:

```text
Merchant Login
    ↓
Upload Product Media
    ↓
Media Becomes READY
    ↓
Associate With Product
    ↓
Publish Product
    ↓
Storefront Displays Media
```

---

## 49. Demo Simplifications

The Demo does not require:

- Multi-region object storage.
- Advanced image transformation infrastructure.
- Dedicated media-processing services.
- Video transcoding.
- Advanced digital asset management.
- Complex media permissions.
- Global media deduplication.
- Multi-CDN routing.

Object storage plus a clean application abstraction is sufficient.

---

## 50. V1 Evolution

The same Media boundary can later support:

- CDN integration.
- Image transformations.
- Responsive image variants.
- Video processing.
- Malware scanning.
- Media optimization.
- Lifecycle policies.
- Storage tiers.
- Cross-region replication.
- Advanced media libraries.

These improvements should remain behind the Media capability boundary.

---

## 51. Definition of Done

The Media implementation is complete when:

```text
[ ] Media entity exists
[ ] Store ownership is enforced
[ ] Object storage is used for binary data
[ ] PostgreSQL stores authoritative metadata
[ ] Object keys are server-generated
[ ] Filename input is safely handled
[ ] File type validation exists
[ ] File size limits exist
[ ] Upload lifecycle exists
[ ] Failed uploads are handled
[ ] READY state requires verified storage
[ ] Media deletion is supported
[ ] Product media association works
[ ] Media ordering works
[ ] Public/private visibility is enforced
[ ] Cross-tenant access is prevented
[ ] Object-storage credentials are protected
[ ] API contracts exist
[ ] Database constraints exist
[ ] Appropriate indexes exist
[ ] Idempotent association behavior exists
[ ] Required events exist
[ ] Required cleanup jobs exist
[ ] Unit tests exist
[ ] Integration tests exist
[ ] Security tests exist
[ ] E2E media workflow works
[ ] Documentation matches implementation
```
